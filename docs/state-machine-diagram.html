State Definitions & Transitions
State Meaning Who Owns It Transitions To
ACTIVE Developer A is actively working on the file/function Developer A's Claude COMPLETED
LOCKED High risk conflict detected. Developer B's attempt is blocked. Awaiting decision. Conflict Detector COLLABORATE, WAITING, or auto-cleared
WAITING Developer B chose to wait. Claude is paused/sleeping, subscribed to wake event. Developer B's Claude RESUMED (on lock_removed event)
COLLABORATE Developer B reached out to A. Both notified to sync up offline/realtime. Developer B + A COORDINATED or WAITING
COMPLETED Developer A finished. Work is done. Lock can be removed. Developer A's Claude LOCK_REMOVED → fires event
RESUMED Developer B's Claude wakes up after lock removed. Resumes from checkpoint. Developer B's Claude ACTIVE (now generating)
Event-Driven Wake-Up Mechanism

📤 lock_removed Event

When Developer A finishes and logs completion, the system fires a lock_removed event in the shared log.

🔔 Subscription

Developer B's Claude is subscribed to this event (not polling). It's asleep until the event fires.

⚡ Instant Wake

Event fires → Claude wakes up immediately with full context (what it was about to do, where it paused).

✅ Auto-Resume

No manual intervention needed. Claude continues generating from exact checkpoint without losing context.

# Developer B's Claude logic (pseudo-code) if high_risk_conflict: # Enter WAITING state checkpoint = { "intent": "add validation to login_user", "region": "lines 25-35", "context": current_generation_context } activity_log.save_checkpoint("dev-b", checkpoint) # Subscribe to event activity_log.on_event("lock_removed", callback=resume_generation) # Sleep - no polling, no busy waiting await event_received() # When event fires: def resume_generation(event): checkpoint = activity_log.load_checkpoint("dev-b") resume_from_context(checkpoint["context"]) # Continue generating as if it never stopped
When Developer B Encounters HIGH Risk Lock

💬 Collaborate

Action: Developer B's Claude surfaces message: "Developer A is working on this. Want to reach out and work together?"

Outcome: Both developers can sync offline, pair program, or divide work. State: COLLABORATE

⏸ Pause & Wait

Action: Developer B's Claude enters WAITING state. It saves checkpoint, suspends, subscribes to event.

Outcome: No busy-polling, no wasted tokens. Wakes automatically when lock clears. State: WAITING

🔕 Request Wrap-Up

Action: Developer B's Claude notifies Developer A: "We have parallel work. Can you wrap up soon?"

Outcome: A gets context that someone is waiting. May expedite or coordinate. Shared visibility.

Why This Architecture is Powerful

🎯 No Busy-Polling

Agents sleep until event fires. Zero CPU/token waste while waiting. Event-driven, not time-driven.

🔄 Automatic Context Preservation

Checkpoint saved before sleeping. When woken, Claude resumes with exact context, generation state, intent.

🤝 Enables Real Collaboration

Not just blocking—actively surfaces collaboration options. Developers can choose to work together.

📊 Full State Visibility

Every transition logged. Who's working where, who's waiting, who's collaborated. Complete audit trail.
